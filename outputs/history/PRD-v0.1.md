# LifeFlow 产品需求文档（PRD）

版本：0.1｜日期：2026-11-06｜状态：第一阶段需求稿，待审核。

## 1. 文档与项目状态

LifeFlow 是面向大学生及年轻用户的 AI 智能生活助理，同时用于《生成式人工智能应用基础 II》课程的软件工程实践。价值在于让自然语言请求转化为经过校验的日程、任务和饮食操作，并反馈实际结果。

当前只有文档交付；所有 MVP 功能均未实现、未进行运行验收。本稿不得作为已上线功能说明。用户原始要求构成已确认基线；本稿新增的交互细节、规模和指标均为建议，审核通过后才冻结。验收用例中的样例数据仅为未来测试夹具。

关联文档：[验收标准](docs/ACCEPTANCE.md)、[初步产品设计](docs/PRODUCT_DESIGN.md)、[Agent 安全](docs/AI_AGENT_SAFETY.md)、[技术风险](docs/TECH_RISKS.md)、[阶段计划](docs/ROADMAP.md)、[变更记录](docs/CHANGELOG.md)。

## 2. 目标与成功条件

### 2.1 产品目标

- 帮助用户把课程、学习任务和生活安排放进可执行的日程，减少冲突和遗漏。
- 通过食物库与照片辅助录入，降低饮食记录成本，展示热量及基础营养统计。
- 用户通过 AI 对话查询数据、添加普通事项、提出规划请求；既有重要安排和删除操作受到保护。
- 桌面本地运行可靠，移动端操作顺畅；如实说明 PWA 和本地服务依赖。

### 2.2 课程交付目标

形成需求—设计—实现—迭代—测试—验收的证据链。交付完整源码、README、配置示例、测试记录、真实问题记录和必要 Git 历史。最终代码需提交至 Gitee；远程地址、推送操作及部署必须另行取得用户授权，不在本轮执行。

### 2.3 第一版完成定义

M01—M14 全部满足已审核验收标准；真实 DeepSeek 调用、业务工具执行和视觉识别均有脱敏证据；核心业务在重启后保留；手机访问和 PWA 限制完成实测说明。未验证、阻塞或失败项不得计为通过。若设备、API 或数据授权不具备，保留缺口并提交范围变更，由用户决定。

## 3. 目标用户与核心场景

| 用户               | 需求与痛点                                   | 成功场景                                                       |
| ------------------ | -------------------------------------------- | -------------------------------------------------------------- |
| 大学生             | 课程固定，作业与复习任务分散，难估算空闲时间 | 输入“两小时概率论、一小时英语”，系统避开已有课程，排入指定窗口 |
| 时间规划用户       | 临时安排打断计划，不想逐条重排               | 选定受影响的未完成学习任务，预览调整并确认，保留原有重要事项   |
| 饮食管理用户       | 食物份量难记录，不理解热量来源               | 搜索或拍照选食物，修正克数后记录，看到营养来源和估算标记       |
| 重视隐私的本地用户 | 不希望创建账号，希望保有自己的数据           | 数据存电脑本地，了解何时向 AI 服务发送内容，可导出并清理       |

不将疾病管理、医疗诊断、专业营养处方或无人监督的自动决策作为产品目标。

## 4. 使用环境与运行边界

已确认技术方向：React + TypeScript + Vite、Tailwind CSS、Node.js + Express、SQLite、DeepSeek API、视觉模型 API 待评估、PWA、Git + Gitee。未经用户确认不替换核心技术。

第一版为单用户系统，无注册登录、账号体系和云端同步。建议电脑上的 Express 与 SQLite 构成唯一业务数据源；手机通过网络访问同一服务。这是对既定技术栈的初步落地建议，非第二阶段完整架构设计。

手机访问条件包括电脑开机且服务运行、网络可达、防火墙与监听配置正确，以及适配 PWA 的可信 HTTPS。手机里的 `localhost` 指手机本身；打开局域网 HTTP 页面不代表 Service Worker、安装和全部 API 都正常。安装 PWA 不会在手机上启动 Node.js 或复制 SQLite。AI 还依赖电脑能访问第三方 API。详细条件与验证矩阵见技术风险文档。

建议基础 PWA 只保证安装引导、应用外壳缓存和明确的断连提示；完整离线增删改与自动同步不作为隐含承诺，见 D01。

## 6. MVP 业务需求与规则（细化建议待审核）

### 6.1 今日概览（M01、M03、M07）

显示所选时区当天日期、按开始时间排序的日程、当天待办和完成进度、摄入与目标、AI 规划入口。建议“当天待办”定义为截止日在今天或已关联今天日程的任务并集；逾期任务单独标示，无日期未安排任务可从任务面板进入。进度分子为该集合中已完成任务数，分母为集合总数；零任务显示“暂无任务”，不出现除零。只有成功落库的饮食计入摄入。

### 6.2 时间与日历（M02、M04）

- 日程包含标题、开始、结束及可选备注；标题去空白后不得为空，结束严格晚于开始。
- 支持跨午夜事项，在涉及日期均可看到；使用半开区间 `[开始, 结束)`，前一事项结束等于后一事项开始不冲突。
- 建议使用用户时区解释自然语言日期并在回执中写出完整日期、时区；初始建议 Asia/Shanghai，可在设置调整。实际存储格式与夏令时处理在第二阶段确定。
- 冲突定义为两个事项 `A.start < B.end 且 B.start < A.end`；更新时排除自身，跨日同样检测。
- 建议手动冲突操作提示冲突对象并阻止保存，用户修改时间后重试；AI 不获得忽略冲突的权限，见 D02。临时有事先加入忙碌时间，原受影响任务需确认调整，不能暗中覆盖。
- 所有已有日程默认受保护。用户手动表单提交是本次编辑意图；删除需明确确认。AI 对既有事项的调整需展示前后差异并确认。

### 6.3 任务（M03）

任务包含标题、低／中／高优先级、可选截止日期时间、预计耗时（正整数分钟）、未完成／已完成状态。建议默认中优先级、预计 30 分钟并允许修改；仅日期截止按用户时区当日结束解释并显示。归档、子任务、习惯打卡不纳入 MVP。

任务是要完成的工作，日程是占用的时间。任务安排入日程不等于完成；时间过去不自动完成。MVP 建议一个任务至多关联一个有效计划日程，未完成任务才进入规划。删除关联日程不删除任务；删除关联任务前明确提示关联日程处置，默认一并删除须在同次确认中列出。完成标记不自动删除日程，历史占用保留。见 D03。

### 6.4 AI 时间规划（M09）

用户指定日期、可用窗口和任务；未提供的必要信息由系统澄清，不能猜测任务耗时或含糊的时间意图。建议将“下午”解析为 13:00—18:00 的候选窗口，明确展示并允许修改；若未确认此默认，则追问具体范围。不能把样例默认偷换成用户确认。

规划读取指定窗口的已有日程与目标任务，求空闲区间；限制在作息及用户指定窗口交集内。建议排序为截止时间较近优先、同截止下高优先级优先、再按创建顺序；无截止排在有截止之后。规划不早于当前时间，不排在截止后。过期任务提示用户修改截止或处理，不擅自顺延。

第一版建议任务不拆分，寻找可容纳整个耗时的连续区间；空间不足列出未安排任务及分钟缺口，不缩短耗时、不挤占已有事项。用户只请求方案时不写库；明确请求“帮我安排”时，可自动执行不冲突的普通新增并展示结果。批量新增作为一次可审核操作集合，全批次提交前重新检测冲突；建议原子提交，失败不留下半套计划。

“重新安排”在 MVP 中限于用户明确选择的未完成关联任务、明确日期窗口、展示差异并确认后的单次调整。跨周滚动、不断自动优化、后台无人值守重排属于未来扩展。见 D04。

### 6.5 饮食与营养（M06、M07、M11）

- 食物库条目具有名称、类别、生／熟或烹饪状态、每 100g 可食部热量与三大营养、来源标识及来源版本／日期。建议首批不少于 50 项，覆盖主食、肉蛋、水产、奶豆、蔬果、油脂等常见类别，最终数量与数据授权待 D05 确认。
- “一碗／一份”必须有可见克数换算依据，否则要求输入克重。采用 `每100g值 × 克重 ÷ 100` 计算。统计基于未四舍五入值合计后展示；建议热量保留 1 位、营养克数保留 1 位。
- 来源无某营养数据时显示“未知／数据不全”，不得按 0 伪造。未匹配食物先让用户选库内条目；无可靠来源时可保留估算草稿，不能伪装成精确营养条目。
- 记录包含用餐日期时间、餐次、多个食物及克重、营养快照、数据来源、手动／照片／估算标记。修改库中条目不追溯改写已保存历史快照。编辑／删除记录后统计重新计算。
- 照片流程必须分别展示食物识别、份量估算和营养计算。AI 识别结果与估算克数均可修改；确认前不形成正式饮食记录或摄入统计。未知用油、混合菜、遮挡等展示不确定性，不能声称从单张照片精确测量质量。
- 目标有减脂、增肌、维持、均衡四种；用户手工设置热量与三大营养参考值。建议选择目标不自动推导医学含义的推荐数字，也不强制采集身高体重。目标未设时展示实际摄入及“未设置目标”，不出现无依据的推荐值。
- 基础历史支持按日期查看饮食与日汇总，建议最近 7／30 天列表；无记录日期标为“未记录”，不解读为实际摄入为 0。建议可手动浏览更早日期。历史目标保留当时快照，避免修改当前目标重写旧比较基线，见 D06。

### 6.6 对话和工具（M08、M10）

独立页与全局入口访问同一当前会话和业务状态。AI 可以解释、查询并通过后端白名单工具操作；不直接执行 SQL、脚本或模型生成的任意请求。每次修改均进行参数、实体归属、业务规则、权限与必要确认校验。仅在数据库提交成功后显示“已创建／已修改”，提供对象与时间等结果卡片。失败、部分读取、取消、待确认和未知执行状态分别展示。

普通新增自动执行的授权限定于用户当前明确意图，不是模型随意补充事项的授权。图像饮食始终确认；删除、既有日程迁移、覆盖目标、批量清理等高风险行为确认后才能执行。最小化向第三方发送数据；首次发送前说明范围与用途并取得同意。安全规则详见 Agent 文档。

### 6.7 设置与数据（M05、M12）

设置作息窗口、时区、饮食目标、主题（浅／深／跟随系统）及非密钥 AI 选项。密钥只由本地服务端环境变量提供；设置页显示是否配置、当前允许的模型与连接状态，不回显密钥、不让前端保存密钥。模型白名单、预算与超时在第二阶段确定。

建议本地数据管理至少有结构化业务数据导出、验证后的恢复导入、清空数据三项。导入／清空必须预览影响、确认并有可恢复备份；导出不包含密钥，照片默认不留存。清空同时清理相关会话／缓存，避免页面重新显示已删内容。具体备份和导入策略待 D07 确认。

## 7. 非功能需求（指标建议）

| 类别      | 需求                                                                                                      |
| --------- | --------------------------------------------------------------------------------------------------------- |
| 可用性    | 360、390、768、1440 CSS px 宽度可操作，正文无横向溢出；周视图可用内部滚动或日期切换                       |
| 可访问性  | 关键触控目标建议不小于 44×44 CSS px；表单有标签，错误有文本，支持键盘与焦点，普通正文对比度目标 4.5:1     |
| 视觉      | Apple 风格简洁层级与留白，统一圆角；浅深色均测试；减少动态效果设置下关闭非必要动画                        |
| 可靠性    | 后端失败不显示保存成功；确认与重试不重复写入；恢复后重新读取服务端状态                                    |
| 性能      | 建议在 500 日程＋500 任务＋1000 饮食记录下，20 次本地非 AI 查询的响应 p95 ≤1s；环境、样本、计时范围需记录 |
| 隐私      | 密钥不入客户端、仓库和日志；仅本地持久化业务数据不代表 AI 调用完全离线                                    |
| 可维护性  | 业务规则统一在服务端；文档、测试、需求 ID 与提交关联；不提前建设多租户平台                                |
| AI 可用性 | 网络、密钥或余额异常时，手工日程／任务／食物库仍可在本地后端可达时使用                                    |

## 8. 验收与可追溯性

每个 M 编号对应 [ACCEPTANCE.md](docs/ACCEPTANCE.md) 的具体输入、操作和预期结果。测试区分人工夹具、受控异常响应与真实 API 联调；前两者不能证明第三者成功。当前所有业务用例状态为“未执行”。

建议最终演示串联：建课程 → 建任务 → 请求明日规划 → 验证不冲突与持久化 → 确认一次调整 → 食物库记录 → 真实照片识别后修改确认 → 目标统计 → 手机访问与 PWA 断连边界。不得用预制聊天内容冒充真实请求。

## 9. 待用户审核的设计决策

以下均不减少原始必做功能；如用户要求更强能力，需要评估工作量并记录变更。

| ID  | 建议方案                                                 | 需要确认的边界与影响                                                        |
| --- | -------------------------------------------------------- | --------------------------------------------------------------------------- |
| D01 | 电脑本地后端为主，手机局域网客户端；基础离线仅外壳／提示 | 是否接受手机不能脱离电脑独立运行；选择真机与本地可信 HTTPS 验证方式         |
| D02 | 手动冲突也阻止保存，已有日程默认受保护                   | 是否需要“知情后允许手动冲突”的例外；若允许须重新定义验收，AI 仍不得忽略冲突 |
| D03 | 任务单一关联日程，分钟耗时，不自动拆分；关联删除规则明确 | 默认耗时、仅日期截止语义、完成与日程保留是否合适                            |
| D04 | 明确窗口的一次性规划与指定未完成任务调整                 | 默认下午窗口、排序规则、原子提交及确认边界；完整动态重排仍为未来扩展        |
| D05 | 可溯源本地食物库，首批建议 ≥50 项；视觉服务独立评估      | 食物来源／许可、中文覆盖、视觉供应商／模型、调用预算及照片测试样本          |
| D06 | 用户自定营养参考数值；基础历史列表＋目标快照             | 是否接受不自动计算个体热量建议；7／30 天入口及四类目标的交互                |
| D07 | 导出、校验导入恢复与清空；照片默认临时处理               | 本地数据管理最低范围、保留策略、发送第三方前的同意与 LAN 访问保护           |
| D08 | 采用本稿验收矩阵、设备记录与性能／识别目标               | 可提供哪些真机和 API；课程截止时间与预算尚未知，暂不承诺日程工期            |
